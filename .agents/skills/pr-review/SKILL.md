# pr-review

PR を「主張する前に検証する」方針でレビューし、そのまま貼れるコメント案を提示するスキル。
**検証は敵対的に、文章はやわらかく。**
レビューコメントは文面の提示までを行う。投稿・返信は明示依頼があり、文面承認を得た場合のみ。

## 手順

### 1. PR の把握

- 引数や会話から PR を特定する。不明なら `gh pr list` で候補を出して確認する
- `gh pr view <番号> --json title,body,author,baseRefName,headRefName,files` で本文と変更ファイルを取得
- `gh pr diff <番号>` で差分をスクラッチパッドに保存して読む
- 返信案も作るときは既存コメントを取得する（未解決スレッド中心に）
  ```bash
  gh api repos/{owner}/{repo}/pulls/<PR>/comments --paginate
  gh pr view <PR> --comments
  ```
- **PR 本文の「背景・目的・スコープ外・設計判断」を先に読む**。スコープ外と明記された事項への指摘は出さない（スコープ外リストへの追記提案は可）

### 2. 周辺コードの読解

周辺コードまで読んでから判断する（diff 単体で判断しない）。最低限これらを確認する:

- 変更された関数の呼び出し元すべて（`grep -rn` で列挙）。再試行・バッチ・cron 経路があるか
- 変更コードが呼ぶ既存関数の実装（コスト・キャッシュ有無・返り値の意味）
- 失敗時の値（エラーマーカー等）が下流でどう扱われるか
- 対象リポジトリの規約ファイル（`CLAUDE.md` / `AGENTS.md`、spec や steering の類。該当領域のみ）。規約違反の判定基準にする

### 3. 指定観点の精査

ユーザーが観点を指定した場合（例: API 呼び出し回数、テスト網羅性）は最優先で調べ、
**問題が無くても「無い」ことを根拠つきで報告する**（例: 「整合判定は取得済みレスポンスの再利用のみで外部呼び出しは増えない」）。

### 4. 検証駆動の指摘（このスキルの核）

- **主張する前に実行して確かめる**。エッジケースの挙動は `uv run python -c` 等で
  既存関数に実入力を食わせて確認する。推測のまま指摘しない
- **実在性を問う**。理論上のエッジケースは「そのケースが実データに存在するか」を確認してから深刻度を決める:
  - 手元にサンプルデータがあれば grep で確認
  - DB クエリで白黒つくなら、そのクエリを提示する
  - 確認できなければ、その旨を明記して [ask] に格下げする
- **修正提案は副作用を検討する**。提案した修正が別の穴を開けないか（トレードオフの付け替えになっていないか）を確認し、両面あるなら正直に書く
- 失敗の倒れる方向を評価する（安全側=空欄/エラー vs 危険側=誤データ採用）。安全側に倒れる問題は深刻度を下げる
- 可能なら lint / typecheck / test をローカルで実行して判断材料にする。PR をローカルに checkout するのは作業ツリーが clean な場合のみ（ユーザーの作業中ブランチを壊さない）。checkout したブランチでは読む・実行するだけにとどめ、変更を加えない

### 5. 敵対的検証

対象は PR だけでなく自分の指摘も含む。

- **PR の主張に反例を作りにいく**。docstring・コメント・PR 本文が主張する不変条件
  （「〜の場合は必ず〜になる」「〜は起きない」）に対し、崩れる入力を最低 1 つ構築しようと試みる。
  構築できたら検証（手順 4）へ、できなければ何を試したかごと主張を信頼する
- **自分の指摘を潰しにいく**。報告する前に「この指摘を無効化する事実は何か」を一度探す
  （既に防御されている・到達しない経路・実データに存在しない等）。潰れたら報告しないか [ask] に格下げする
- **テストを疑う**。テストが pass することと分岐を検証していることは別物:
  - 実装のどこを壊したらこのテストが落ちるか。落とせない分岐＝未検証として指摘候補にする
  - アサーションが実装と同じ誤りを共有していないか（フィクスチャを実装のロジックで組み立てている等）
  - 既存テストの修正が入っていたら「なぜ修正が必要になったか」を疑う
- 楽観と悲観を分ける: 見つからなかったことは「無い」ではなく「この方法では見つからなかった」と報告する

見落としやすい観点:

- **後方互換**: 既存の呼び出し元・既存データ・API レスポンス形が壊れないか
- **横断影響**: 定数・設定・命名の追加は関連リポ／他サービスも grep して衝突や取りこぼしを見る
- **PR 説明との整合**: 背景・目的に対して diff が過不足ないか（書いてあるのに入っていない変更、説明にない変更）
- **セキュリティ・権限**: テナント境界を跨ぐクエリ、認可チェックの欠落、機微情報のログ出力
- **正しさ**: null / 空 / 0 件 / 境界値 / 重複 / 並行実行、エラーパス、トランザクション境界
- **過剰設計**: 実装 1 つしかない抽象、呼び出し元 1 つの層、誰も設定しない config、
  標準ライブラリ／プラットフォーム機能で置き換えられる自前実装、1 回の利用のために足した新規依存。
  見つけたら「何を消して何で置き換えるか」を 1 行で書く。分類は ponytail-review の
  delete / stdlib / native / yagni / shrink に従うが、`L42: yagni: ...` 形式は内部の診断用にとどめ、
  コメント案は手順 7 の文体で書く。差分内のコードに限り、差分外の既存設計へは広げない

### 6. ラベルの付け方

| ラベル | 使いどころ |
|---|---|
| [imo] | 根拠（再現・データ・実測）のある意見・提案 |
| [suggestion] | 具体的な代替案・コード例を添えた改善提案（採用は作者判断） |
| [ask] | 質問・スコープ確認・**データ未確認の懸念** |
| [nit] | 細かい改善（typo・命名・フォーマット等）。無くても困らない |

- **検証できなかった懸念は [ask] にする**。[imo] は検証を通ったものに限る
- 過剰設計の指摘は、置き換え案を添えるなら [suggestion]、消すだけで済むなら [nit] にする。動作上の実害は無いので [imo] にはしない
- [suggestion] で数行程度の差分を示す場合は、GitHub の ```suggestion 記法で書くと作者がワンクリックで適用できる
- 明確なバグ（再現済み・実害あり）はコメント案とは別に報告の冒頭で強調する。別の重大度タグは作らず、本文で影響の大きさが伝わるように書く
- コメント数は絞る（目安 5 件以内）。同種の指摘はまとめる

### 7. 文面

**内容の厳しさは根拠で担保し、言い回しはやわらかく保つ。** 提案・疑問の形で書き、断定・命令調は使わない。

| 避ける | 使う |
|---|---|
| 〜しませんか / 〜すべきです | 〜すると良さそうです！ |
| 〜が間違っています | 〜になっていそうです |
| 〜してください | 〜はどうでしょう |
| 〜が要ります / 〜が必要です | 〜しておくと安心そうです |
| 〜を明記してほしいです | 〜を書いておくと良さそうです！ |

**この規則はコメント案だけでなく、チャットで返す本文（「見つけた問題」「総評」）にも同じく適用する。**
貼る文面だけやわらかくして報告本文が命令調になっていると、そのまま転記されたときに調子が変わる。

- **当為表現（すべき・要る・必要・明記してほしい）を提案表現へ寄せる。** 深刻度は語尾ではなく、
  影響（何がどう壊れるか）を具体で書いて伝える
- 「！」は提案の語尾に**適宜**付けて角を取る。全文末に付けると軽くなるので、1 コメントに 1 つ程度、
  相手に動いてもらう提案の箇所に絞る

- 小難しい用語を使わない。相手が辞書を引かずに読める平易な日本語で書く
  - チームで通じる普通の言葉を選ぶ（「テストの射程外」→「テストのスコープ外」）。もったいぶった言い換えをしない
- **何がどうなるかを具体で書く**。カギ括弧で抽象語を強調する書き方（「完全」として扱う、「正しい」状態、等）にしない
  - 悪い例: 「打ち切られた一覧を「完全」として照合すると誤判定します」
  - 良い例: 「打ち切られた一覧のまま照合すると、3000 件より後のファイルが判定から漏れます」
  - 「bogus な値」→「実在しない値」。定着した技術用語（フォールバック等）はそのままでよいが、説明で済む英語スラング・略語は日本語に開く
- **比喩や擬人化を使わず、列名・状態値・テーブル名で書く。** 設計文書やコード内の比喩（生存者・兄弟・走る・生える・倒す等）をレビュー本文へ持ち出さない。読み手が実物を特定できず、指摘の裏を取れない
  - 悪い例: 「走っている兄弟が居ないので、倒しても仕事を奪いません」
  - 良い例: 「同じ `order_id` に `PENDING` / `RUNNING` のジョブが無いので、`CANCELED` にしても他のジョブの状態は変わりません」
- 何をどこに書いたかまでで止める。対応の中身に関係ない気配りの説明（「〜さんにも伝わる位置に置いています」等）は足さない
- 語尾は複数の形を混ぜる（「〜だと良さそうです」「〜はどうでしょう」等）。「〜だと嬉しいです」のような同じ語尾を繰り返さない
- 依頼・お願いにあたる文には 🙏 や 🙇 を適宜添える。毎コメントではなく、相手に手を動かしてもらう箇所に絞る
- **事実 → 質問・提案の順で書く。** 「〜がはっきりしました」「〜は納得しました」「〜で良くなりました」等、
  相手の変更や判断を追認する前置きから入らない
  - 悪い例: 「更新後の説明で、通知が落ちたジョブが `RUNNING` で残ることがはっきりしました。この状態だと〜」
  - 良い例: 「通知が落ちたジョブは `RUNNING` のまま残ります。この状態で再試行バッチが `ERROR` にすると〜」
- **断定できることは言い切り、確認したいことは疑問文にする**。同意を誘導するタグ
  （「〜ますよね」「〜ですよね」）は付けない
  - 悪い例: 「両方に載るようになりますよね。」
  - 良い例: 「両方に載ります。片側を除く必要がある、という理解で合っていますか？」
- 良い例:
  - `[suggestion] ここ、tenant_id の絞り込みが無いので他テナントの行も返ってきそうです。where 句に足すと良さそうです！`
  - `[ask] この分岐、既存の cron 経路でも通る想定でしょうか？ 通るとすると二重エンキューになりそうな気がしてます`
  - `[nit] typo: recieve → receive になってます`

#### 既存コメントへの返信

- 対応した事実と理由をそのまま書く。「ご指摘のとおりです」など相手の指摘を評価する言い回しは使わない
  - 悪い例: 「ご指摘のとおりです。per_page=100 を追加しました」
  - 良い例: 「per_page=100 を追加しました。往復回数の観点が抜けていました」
- 自分に抜けていた観点を指摘されたときは、一言だけ感謝を添える。定型の枕詞として毎回付けるのではなく、実際に見えていなかった指摘に限る
  - 「！」や 🙏 🙇‍♂️ をたまに混ぜる。毎回ではなく数回に一度、感謝の強さに合わせて。同じ返信セットの中で連発しない
  - 良い例: 「往復回数の観点が抜けていました、助かりました！ per_page=100 を追加しました」
  - 良い例: 「実測込みの検証ありがとうございます🙏 挙動差はコメントに明記する形で対応しました」

### 8. 出力形式

結論から。最終メッセージに以下をまとめる:

```markdown
## レビュー結果: <PR タイトル> (#<番号>)

### 指定観点の合否
（観点の指定があった場合。問題なしなら根拠つきでその旨を明記）

### 見つけた問題
（検証済み / 未検証を区別。再現手順や実行結果を添える）

### コメント案
#### 1. `path/to/file.py:123`
[suggestion] 〜〜すると良さそうです！
（必要なら ```suggestion ブロックでコード例）

#### 2. ...

### 既存コメントへの返信案
（未解決スレッドがある場合のみ。スレッドごとに引用 → 返信案）
> @reviewer: 元コメントの要旨
返信案: 〜〜

### 総評
（テスト構成の良い点も含める。指摘ゼロなら「妥当」と言い切る）

### 検証ログ
（実行した lint / test の結果、裏取りに読んだ箇所を簡潔に）
```

- コメント案はそのまま GitHub に貼れる文面にする
- コメント案には**貼る位置を `file:line` で明示する**（次の手順 9 で inline 投稿するため）。作者のコード内表記（手順番号やセクション名）を引用すると伝わりやすい
- 指摘ゼロなら「特に問題なさそうです」+ 確認した観点を報告する。無理に指摘を作らない

### 9. 投稿（明示依頼 + 承認があった場合のみ）

**既定は該当行への inline review コメント。** PR 全体に対する話（総評・スコープ確認・複数ファイルにまたがる設計の話）だけ通常の issue コメントにする。

```bash
# 複数の inline をまとめて 1 レビューとして投稿する
gh api repos/{owner}/{repo}/pulls/<PR>/reviews -X POST \
  -f event=COMMENT \
  -F 'comments[][path]=path/to/file.py' -F 'comments[][line]=123' \
  -F 'comments[][side]=RIGHT' -F 'comments[][body]=[imo] ...'
```

- inline は **その PR の diff に含まれる行にしか付けられない**。指摘先が差分外のファイルのときは、(1) 差分内で最も関連の深い行に inline で貼り本文で差分外の `file:line` を示す、(2) それも不自然なら通常コメントにする — の順で検討する
- ` ```suggestion ` 記法は inline でのみ機能する。通常コメントへ落とすときは普通のコードブロックに変える
- stack PR では、指摘した実装が載っている PR に貼る。別 PR で顕在化する場合はそちらへ導線コメントを 1 本置く
- 投稿後は PR ごとのコメント URL を一覧で報告する

## 禁止事項

- **レビュー対象ブランチへの commit / push / force-push**。レビューは読む・実行して確かめる・文面を提示するまでで、
  コードを直すのは作者の仕事。修正案は ```suggestion 記法か diff の提示で渡す
  - 自分が作者の PR であっても、pr-review の実行中は同じ扱い。修正を頼まれたらスキルを抜けて別の指示として受ける
  - 検証で一時的に手を入れた場合（デバッグ print・試験スクリプト等）は `git restore` / `git clean` で必ず元に戻し、
    元のブランチへ `git switch` してから終了する
- レビューコメント・返信の自動投稿（文面提示まで。投稿は明示依頼 + 承認後のみ）。`gh pr comment` / `gh pr review` を勝手に実行しない
- 憶測での指摘。指摘は必ずファイル・行・根拠を伴う。確信が持てないものは [ask] に落として質問の形にする
- 差分に現れないコードベース全体の一般論指摘
- スコープ外と明記された事項への修正要求
